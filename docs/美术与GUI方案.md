# 蜀汉突围 · 美术与 GUI 方案评估

> **制定日期**：2026-10-08
> **用途**：回答"现在能不能推美术、上 GUI、走哪条技术路线"。
> **配套文档**：[`路线图.md`](路线图.md)（阶段门槛与设计方法）、[`../tools/生成州域对照图.py`](../tools/生成州域对照图.py)（地图数据与渲染的样例）
>
> **一句话结论**：**能，而且比你原以为的更早。**推荐走「Web 前端 + Python 引擎」，
> 因为引擎与界面之间的数据桥**已经写好了**，地图渲染这条路**也已经被州域对照图验证过了**。

## 📌 决策记录（2026-10-08 当天更新）

**最终选了 ③ tkinter，而不是本文原先推荐的 ① Web。** 原因是需求中新增了一条硬条件：
**"独立的可运行 .exe 文件"**。这条条件改变了最优解：

| 需求 | Web 方案 | tkinter 方案 |
| :--- | :--- | :--- |
| 独立 exe、双击即玩 | ✗ 需要内嵌浏览器或要求目标机装浏览器 | ✅ 单文件 exe，11 MB，双击即玩 |
| 目标机器零安装 | ⚠️ 需要浏览器（虽普遍存在） | ✅ 连 Python 都不需要 |
| 保持"零第三方依赖"招牌 | ✅ 但多一门 JS 技术栈 | ✅ **tkinter 属标准库**，招牌完整保留 |
| 美术上限（排版/沙盘） | ★★★★★ | ★★ |

**结论：本轮优先"能玩、能发、能双击"，把美术上限留给后续。** 具体做法是把架构留出换壳的余地——
界面**不含任何规则**，所有判定与结算都通过 `src/游戏接口.py` 走引擎，因此：

- 将来若要换成 Web 或 PySide6，**只需另写一个外壳**，引擎与测试一行都不用动；
- 本轮已经把这层隔离用回归用例钉死了（同策略打满 20 回合，界面路径与引擎主循环**逐字段一致**）。

第 3 章的技术选型对照因此**依然有效**，只是它现在的用途变成了"下一轮换壳时的选型依据"，
而不是"本轮该选谁"。

## 一、重新评估：我把门槛定严了（对自己的修订）

`路线图.md` 原来写的是：地图成图要等「地图数据模型定稿（周期 3）」，UI 切图要等「GUI 框架尺寸定稿（周期 5）」。

**重新推敲后，这个门槛定得过于保守。**真正被卡住的只有一件事：**尺寸与坐标系**。而：

| 我原来的说法 | 修订后的准确说法 |
| :--- | :--- |
| 地图成图要等"地图数据化完成" | ❌ 过于保守。**只要先做一次「地图规格决策」**（范围 / 投影 / 比例尺 / 画布像素尺寸，约 0.5 小时），地图底图就能开工；完整的数据化可以之后慢慢补 |
| UI 切图要等 GUI 框架定稿 | ✅ 这条成立。按钮/边框的切图**必须**等尺寸定稿，否则全废 |
| 美术整体要等玩法稳定 | ❌ 不成立。**美术与玩法可以并行**，前提是界面只"渲染状态"、不含规则逻辑 |

**所以：本周只要花 1 小时做「地图规格决策」，美术这条线立刻解锁。**

## 二、最重要的技术发现：桥已经修好了

做 GUI 最贵的一步通常是"把游戏状态接到界面上"。**而这一步你已经做完了。**

| 已有资产 | 位置 | 对 GUI 的意义 |
| :--- | :--- | :--- |
| **完整状态 ↔ JSON** | `src/save_manager.py` 的 `采集状态()` / `应用状态()` | 界面要显示的兵力、粮草、压力、东吴好感、日期、城池、将领、情报**全都能一次导出**（实测 10 个顶层键 / 1890 字节 JSON） |
| **数值已是配置数据** | `config/*.json` | 改数值不用改代码，界面只需读同一份配置来显示 |
| **地图已经是可渲染的 SVG** | `tools/生成州域对照图.py` → `docs/三国州域对照图.html` | 地图渲染与投影这条路**已经跑通并验证过**（经纬度 → 统一投影 → SVG） |
| **规则全部在引擎里且被测试锁住** | `src/` + 126 项自测 + 74 个用例 | 界面**不需要**（也不应该）复制任何判定逻辑，只管"显示状态 / 发送意图" |

> 换句话说：**GUI 要用的数据，你的引擎已经准备好端上桌了。**

## 三、GUI 技术选型对照

| 方案 | 新增依赖 | 中文/隶书排版 | 地图表现 | UI 控件 | 学习成本 | 作品集效果 | 引擎是否仍零依赖 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **① Web（HTML/CSS + SVG/Canvas）**<br>＋ Python 本地服务 | **无**（前端零依赖；桥用标准库 `http.server`） | ★★★★★<br>CSS 排版最强，隶书可用图片或 webfont 直接放 | ★★★★★<br>SVG 已跑通；Canvas/WebGL 上限最高 | ★★★★★<br>HTML 天生就是界面 | 中<br>（要会一点 JS） | ★★★★★<br>截图/录屏都好看，还能做静态原型页 | ✅ **保持** |
| **② PySide6 / Qt** | ~150 MB | ★★★★<br>`QFontDatabase.addApplicationFont` 可运行时加载 TTF | ★★★★<br>`QGraphicsView` 缩放平移很顺手 | ★★★★★<br>表格/面板/对话框齐全 | 中高<br>（Qt 体系庞大） | ★★★★<br>桌面应用质感强，但分享麻烦 | ❌（`ui/` 层有依赖） |
| ③ tkinter（标准库） | **无** | ★★<br>自定义字体要装进系统，透明与抗锯齿很别扭 | ★★<br>Canvas 无抗锯齿、缩放要自己写 | ★★<br>控件够用但很难美化 | 低 | ★★ | ✅ 保持 |
| ④ pygame / pygame-ce | 中 | ★★<br>中文要自己渲染排版 | ★★★★<br>2D 绘制手感好 | ★<br>控件全部手搓 | 中 | ★★★ | ❌ |
| ⑤ Arcade | 中 | ★★ | ★★★★<br>OpenGL，性能好 | ★★ | 中 | ★★★ | ❌ |
| ⑥ Kivy | 中 | ★★<br>中文与样式需额外配置 | ★★★ | ★★★ | 中高 | ★★ | ❌ |
| ⑦ Godot / Unity | — | ★★★★★ | ★★★★★ | ★★★★★ | **极高** | ★★★★★ | ❌ **等于放弃现有引擎** |

### 结论

- **主线推荐：① Web 前端 + Python 引擎**。理由：排版与地图表现最强（正好压在你的书法＋绘画长处上）、
  数据桥零成本、引擎保持零依赖、作品集展示效果最好。
- **备选：② PySide6**。如果你的偏好是"**桌面应用的手感 + 单文件分发**"而不是"画面与排版"，
  选它；它在表格与面板类界面上比 Web 更省事。
- **不推荐现在做 ⑦**：Godot/Unity 会把 `src/` 的判定、存档、126 项测试全部推倒重来，
  这条路的代价是"从零开始做另一个项目"，而不是"给现在这个项目加一层皮"。

## 四、推荐方案的架构（Web 路线）

```
┌─ 浏览器（ui/web/）───────────────────────────────────────────┐
│  舆图：<svg>（复用州域对照图的投影与坐标数据）               │
│  面板：兵力 / 粮草 / 压力 / 东吴好感 / 回合 / 日期            │
│  菜单：部署将领 · 军事 · 计谋 · 外交 · 结束回合               │
│  ※ 只做两件事：把状态画出来；把玩家的"意图"发回去             │
└───────────────────────┬──────────────────────────────────────┘
                        │ HTTP（仅本机 localhost）
┌───────────────────────┴──────────────────────────────────────┐
│  Python 本地服务（ui/server.py，标准库 http.server）          │
│   GET  /             → 静态页面                               │
│   GET  /api/state    → save_manager.采集状态(游戏.__dict__)   │
│   POST /api/action   → 调引擎函数（军事/计谋/外交/结算回合）   │
└───────────────────────┬──────────────────────────────────────┘
                        │ 单向依赖：ui → src
┌───────────────────────┴──────────────────────────────────────┐
│  引擎（src/，零第三方依赖，规则唯一来源）                      │
│  蜀汉突围.py（判定与主循环）· config_loader · save_manager     │
│  受 126 项自测 + 74 个用例保护                                 │
└───────────────────────────────────────────────────────────────┘
```

**启动方式**（对作品集很关键，一行命令就能演示）：

```bash
python main.py --web      # 起本地服务并自动打开浏览器
```

### 三条必须守住的纪律

1. **规则只留在 Python 里**。JS 不许出现任何"如果兵力 > 守军×1.5 就必胜"这类判断——
   否则规则的唯一来源被破坏，126 项断言保护不到界面层。
2. **单向依赖**：`src/` 不得导入 `ui/`。加一条反向约束测试（`test_architecture.py` 里几行即可）。
3. **零依赖的说法要改准**：从"整个项目零依赖"精确为"**引擎零依赖 + 界面零安装**"，
   README 与 `requirements.txt` 的措辞同步更新（这是诚实，不是退让）。

### 关于"人物绘画欠缺"

这份清单里**只有第 10 项需要人物立绘**，而它排在最后、权重最低。
前 9 项里，你的**书法（#3、#5）与绘画（#7、#9）恰好是主力**。策略游戏的视觉重心本就在舆图与界面，
不在立绘——《三国志》早期作品靠"名字 + 头像框"就撑起了人物感。

## 六、本周最小动作（两件事，不要贪多）

| 动作 | 内容 | 产出 | 估时 |
| :--- | :--- | :--- | :--- |
| **动作 A** | 做「地图规格决策」（清单第 1 项） | `docs/地图规格.md` + 把州域图脚本升级成"游戏地图规格版"（带 5 座城池点位与比例尺） | 1 h |
| **动作 B** | 做「GUI 骨架验证」（清单第 6 项） | `ui/server.py` + `ui/web/index.html`：显示地图与局势，"结束回合"按钮真的驱动引擎跑一回合 | 2–4 h |

做完这两件事，你就同时拿到了：**美术的坐标系**（可以开始画）和**界面的技术可行性**（可以继续堆 UI）。
之后美术与玩法就能并行推进，互不阻塞。

## 七、必须提醒的三件事

1. **GUI 不会让游戏变好玩。** 它是外壳：界面能让人愿意点开，但让人玩第二局的永远是玩法。
   所以 GUI 骨架做完之后，**压力棘轮（`待实现构想.txt` 第 1 条）仍然要修**——不要把玩法修复无限期推后。
2. **不要在 GUI 里复制规则。** 一旦界面出现自己的判定逻辑，同一个规则就有两处实现，
   126 项测试保护不到第二处，你会在某个深夜发现"界面允许强攻但引擎判必败"。
3. **不要在尺寸未定时批量画 UI。** 这条是硬约束（清单第 8 项），违反它的代价是全部重画。
