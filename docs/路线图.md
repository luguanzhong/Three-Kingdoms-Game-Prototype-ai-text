## 一、一句话现状

**能玩、能测、能给别人看，但"赢不了"且"长得丑"。**

- 玩法：20 回合完整闭环、三方博弈、6 将 6 计谋、4 档结局，全都能跑通；
- 问题：**压力棘轮**让好局也被拖死（详见 `待实现构想.txt` 第 1 条），玩家缺少可控的减压手段；
- 表现：纯控制台 + ASCII 态势图，没有任何美术资产；
- 工程：126 项自断言 + 74 个用例、零第三方依赖、配置数据化、存档续局、已发布 `v1.0.0`。

## 二、短期小周期计划

> **周期纪律**（沿用 M1~M6 那套，它被证明有效）：
> ① 每个周期只做一件事，能在一两次坐下来之内收尾；
> ② 开工前先写验收标准，收尾时逐条对照；
> ③ **不许削弱已有测试**（断言只能增不能减）；
> ④ 每个周期结束都要：跑测试 → 更新 CHANGELOG → 提交。

### 周期 1 · 作品集收尾（≤ 1 小时）

| 项目 | 内容 |
| :--- | :--- |
| 目标 | 把求职那条线彻底关掉，此后专心做游戏 |
| 产出 | 补 3 张截图到 `docs/images/` → 在 README 第九节取消对应注释 |
| 验收 | GitHub 首页打开能看到图；`git status` 干净 |
| 为什么先做 | HR 基本不会真的跑代码，图是性价比最高的一步；而且做完就没有"欠着的事"干扰你 |

### 周期 2 · 让好局能赢：压力棘轮修复（半天）

| 项目 | 内容 |
| :--- | :--- |
| 目标 | 玩家有手段对抗压力上涨；"北伐大捷"从"几乎不可能"变成"打得好就能到" |
| 产出 | ① 选定并实现至少一种减压手段（**建议先做「议和」或「连环计」**，参 `待实现构想.txt` 候选 A/C）② 新脚本 `tools/模拟统计.py`：批量跑 N 局，输出结局分布与关键曲线 |
| 技术要点 | 减压数值先放进 `config/`（改数值不用改代码）；压力变化写进日志，可事后复盘 |
| 验收 | 126 项自测 + 74 个用例全绿；新增"减压手段生效"的回归用例；给出**改前 / 改后结局分布对比表** |
| 注意 | 这是**玩法改动**，不是工程改动 —— 走正常流程，别顺手改别的 |

### 周期 3 · 地图数据化（半天~1 天）⭐

| 项目 | 内容 |
| :--- | :--- |
| 目标 | 把"地图"从代码里的一堆坐标，变成一份独立的数据 |
| 产出 | `config/map.json`：城池（名称/坐标/所属州郡/控制方）、道路连接、地形类型、险关与要塞标记；`绘制战区态势图()` 改为**由这份数据驱动** |
| 为什么关键 | **这一周期是美术与 GUI 的前置门槛**。数据模型定下来，美术才有"画什么、画多大、放哪里"的确定依据 |
| 验收 | 改 `map.json` 就能改态势图（不再需要改代码）；地图数据有配置校验（像 `config/` 那样非法即报错）；旧测试全绿 |
| 附带收益 | 现在那张 ASCII 图其实已经是一个"节点图"，抽数据是**顺势而为**，不是重写 |

### 周期 4 · 世界观与剧情设定（1 天，可与周期 3 并行）

| 项目 | 内容 |
| :--- | :--- |
| 目标 | 把"这局到底发生在哪个世界线"写清楚，并为事件文本立规矩 |
| 产出 | `docs/世界观与剧情设定.md`：分叉点声明、时间线锚点表、三方势力立场、人物档案、事件卡格式规范 |
| 验收 | 能据这份文档写出 5 张事件卡并接入游戏（数据驱动，放 `config/`） |
| 为什么不急 | 它不动代码，可以在地图周期并行推进；但**必须在做大量美术之前定稿**，否则地图上的地名、旗帜、人物全要返工 |

### 周期 5 · GUI 技术选型 + 最小外壳（1~2 天）

| 项目 | 内容 |
| :--- | :--- |
| 目标 | 让游戏第一次出现在"窗口"里，而不是终端里 |
| 产出 | 技术选型决策记录（见[第六章](#六gui-与技术选型)）+ `ui/` 最小可运行外壳：显示当前局势 + 态势图 |
| 架构要求 | 引擎（`src/`）**保持零依赖**；新增一条反向约束测试：**引擎不得导入 `ui/`**（单向依赖） |
| 验收 | 窗口能跑起来看到局势；`test_architecture.py` 全绿（含新反约束） |

### 周期 6 · 美术 v1（视情况）

顺序很重要，**先风格稿，后成图**：

1. **风格稿 1 张**（先确定视觉方向，别急着画完）
2. **隶书关键字表**（几十个字，见[第五章](#五书法与隶书怎么落地)）
3. **UI 边框 / 纹样 / 图标**（等 GUI 框架尺寸定稿后再批量做，否则白画）
4. **地图成图**（等坐标体系与风格稿都定稿）

## 三、美术与表现层：阶段门槛表

> **直接回答"什么阶段才可以推进美术"**：
> **考据、风格探索、书法练习现在就能开始，一天都不用等；但"生产级美术资源"必须等两个门槛——
> ① 地图数据模型定稿（周期 3）；② GUI 框架尺寸定稿（周期 5）。**
> 原因很简单：**美术一旦画错尺寸和坐标，全部作废**。这不是流程洁癖，是省钱省时间。

| 美术工作 | 现在能开始？ | 前置门槛 | 说明 |
| :--- | :--- | :--- | :--- |
| 考据（州郡位置、地形、道路、地名沿革） | ✅ **立刻** | 无 | 纯查资料，随时可做，而且是**地图质量的天花板** |
| 视觉方向 / 风格板（绢本？竹简？拓片？） | ✅ **立刻** | 无 | 收集参考图、定色板，成本极低 |
| 书法练习与字表整理（隶书关键字） | ✅ **立刻** | 无 | 见第五章；先定"要写哪些字"，再写字 |
| 事件卡文本 / 剧情写作 | ✅ **立刻** | 无 | 只要世界观定稿即可动笔 |
| 地图坐标数据化 | ⚠️ 需先定坐标体系 | 周期 3 | 统一用一套坐标系（建议经纬度，方便对齐任何底图） |
| ASCII 图改为数据驱动 | ⚠️ | 周期 3 | 为 GUI 铺路 |
| GUI 外壳（窗口、面板、布局） | ⏳ **等** | 周期 5 | 技术选型没定就做界面，等于赌博 |
| 地图底图成图（手绘 / 矢量） | ⏳ **等** | 周期 3 + 风格稿定稿 | 坐标与风格定了再画 |
| UI 切图（按钮、边框、纹样） | ⏳ **等** | 周期 5 框架定稿 | **尺寸未定就批量画 UI = 100% 作废** |
| 人物立绘 | 🚫 **最后** | 系统稳定 + 人物设定定稿 | 最贵、返工率最高、对玩法贡献最低 —— 见下方"你的优势" |

### 关于"会绘画但人物绘画欠缺"——这其实不是短板

策略游戏的视觉重心**根本不在人物立绘**，而在**地图、界面、氛围**。你的技能组合（书法 + 绘画 + 历史兴趣）正好压在正确的重心上：

- **该重投入**：地图质感、界面纹样与边框、战役/事件插图、隶书标题与印章、势力旗帜。
  这些既有辨识度，又能用你的书法与绘画直接产出。
- **该轻投入**：人物。用**符号化处理**替代立绘——旗帜、姓名印章、剪影、脸谱化的极简头像。
  《三国志》系列早期作品就是靠名字 + 头像框撑起人物感的。
- **可以后置**：真要做立绘，也等玩法完全稳定、人物设定定稿之后再说（那时候你会更清楚每个人物该长什么样）。

## 四、地图：从 ASCII 到拟真沙盘

### 4.1 数据先行：一份 `map.json` 该装什么

不做数据化，地图永远只能写死在代码里。建议字段：

```jsonc
{
  "坐标系": "GCJ-02 或 WGS-84 经纬度（选一个，全文统一）",
  "城池": [
    { "名称": "江陵", "州郡": "荆州·南郡", "控制方": "蜀汉",
      "经度": 112.19, "纬度": 30.35, "类型": "坚城",
      "相邻": ["襄阳", "永安"], "地形": "江汉平原" }
  ],
  "道路": [ { "起点": "襄阳", "终点": "樊城", "类型": "水路", "通行": true } ],
  "地形": [ { "名称": "汉水", "类型": "河流", "途经": ["襄阳", "江陵"] } ],
  "要地": [ { "名称": "阆中", "类型": "险关" }, { "名称": "永安", "类型": "要塞" } ]
}
```

**关键设计决策**：坐标统一用**经纬度**（而不是自制的"格子坐标"）。理由：
以后无论你用手绘底图、矢量地图、还是真 DEM 高程做沙盘，**都能直接对齐**；反之如果先用格子坐标，
将来换底图就得全部重标。

### 4.2 素材与考据来源（都是真实可查的公开资源）

| 来源 | 能拿到什么 | 备注 |
| :--- | :--- | :--- |
| **谭其骧《中国历史地图集》** | 历代政区与地名的**权威参考**（东汉、三国各卷） | 中国历史地理的标杆，考据以此为准绳 |
| **CHGIS（中国历史地理信息系统）** | 历史政区**矢量数据**（点 / 面） | 复旦大学历史地理研究中心与哈佛燕京学社合作项目；学术用途需按官网要求注册 |
| **SRTM / ASTER GDEM** | 全球数字高程模型（30m / 90m） | 想做"真地形沙盘"就是靠它；国内可从地理空间数据云等平台下载中国区数据 |
| **Natural Earth** | 免费矢量底图（河流、海岸线、国界） | 公共领域，商用友好 |
| **《三国志》（陈寿）+ 裴松之注** | 人物与事件的一手材料 | 裴注是细节最丰富的一层；不要只依赖《演义》 |
| **《资治通鉴》卷六十五～七十二** | 约 208–228 年的编年记事 | 编年体，最适合抽取"历史锚点" |

### 4.3 范围建议：**不要一上来做全中国**

这是最容易犯的错。你的战场其实只有一条轴线：

> **汉中—秦岭—汉水—襄阳—江陵**（约东西 500–600 公里）

建议做法：
1. **先做局部沙盘**（这条轴线），做到"有地形起伏、有河流、有州郡界、有城池点位"；
2. 局部做好了，往外扩就是复制流程；局部没做好，全中国地图只是一张漂亮的废图；
3. 沙盘的**玩法价值**来自"地形影响行军与粮道"，而不是"面积大"。先想清楚地形在玩法里做什么，再决定画多大。

### 4.4 一个重要的设计取舍：拟真 vs 风格化

| 路线 | 特点 | 成本 | 适合你吗 |
| :--- | :--- | :--- | :--- |
| **拟真沙盘**（DEM 高程 + 写实渲染） | 有真实地形起伏，可做"看得见山"的行军 | 高（数据 + 3D/等高线渲染 + 美术量） | 技术挑战大，但**最能体现独特性** |
| **古地图风格**（绢本 / 拓片 / 手绘） | 像一张古代舆图，隶书标注天然合适 | 中（可用你的绘画 + 书法） | ✅ **和你的技能最匹配，建议做主线** |
| 抽象节点图（现在的 ASCII 图） | 信息清晰，零美术成本 | 极低 | 已经做了，继续作为"调试视图"保留 |

**推荐**：**古地图风格做主线，拟真地形做"图层"**——即在同一套经纬度数据上，
底图用手绘/矢量风格，但**地形起伏（山脉、河流、险关）按真实考据绘制**。
这样既有美术风格，又有地理真实感，还避开了 3D 渲染的坑。

## 五、书法与隶书：怎么落地

**核心结论：你不需要做一套字库。** 做一套能覆盖常用汉字的字库（3000+ 字）是几个月的工作量，
而且屏幕小字号下隶书可读性差。正确做法是**只写"关键字"**：

| 用途 | 字数 | 举例 |
| :--- | :--- | :--- |
| 游戏标题 / 章节标题 | 10~20 | 三国·蜀汉突围、北伐、屯田、计谋、外交、结算 |
| 州郡与城池名 | 20~40 | 益州、荆州、汉中、襄阳、樊城、宛城、上庸、洛阳、成都、江陵、阆中、永安 |
| 按钮 / 菜单文字 | 20~40 | 部署、镇守、强攻、围攻、劝降、火攻、存档、读档 |
| 印章 | 2~4 方 | 蜀汉、北伐都督、军师将军 |
| **合计** | **约 60~100 字** | 一次性写完，之后长期复用 |

**落地方式**：手写 → 高清扫描（或数位板）→ 抠成透明 PNG（或转矢量 SVG）→ 游戏里当图片渲染。
这样隶书只出现在**该出现的地方**（标题、地名、印章），正文用黑体保证可读性。

**三条路线对比**：

1. **自写关键字（推荐）**：完全可控、独一无二、正好练书法；缺点是只能用在你写过的字上。
2. **做成字库**（FontForge 等工具）：只有当你打算"全文隶书排版"时才值得 —— 工作量巨大，不建议现在做。
3. **使用现成隶书字库**：⚠️ **务必先看清授权**——多数商业隶书字库商用需付费授权，
   可免费商用的隶书风格字库较少。若要用，请把授权信息记录下来（哪个字库、什么许可、从哪下载）。

**风格建议**：绢本质感 + 朱红印章 + 隶书标题，成本低、辨识度高、且有文化质感，
正好发挥你书法与绘画的长处。

## 六、GUI 与技术选型

> **先说一个必须澄清的冲突**：项目现在的硬约束是"**零第三方依赖**"，并由架构测试强制保证。
> 而任何 GUI 库都是第三方库。**这不是要放弃约束，而是要把它说准。**

### 推荐的架构处理（不管最后选哪个技术）

```
src/    引擎：判定 / 配置 / 存档          ← 永远零依赖，架构测试继续只扫这里
ui/     外壳：窗口 / 渲染 / 输入          ← 允许依赖 GUI 库
tools/  脚本：模拟统计 / 数据导出         ← 允许依赖（如果要）
```

新增一条**反向约束**：`src/` 不得导入 `ui/`（单向依赖）。
这样"零依赖"从"整个项目"精确收窄为"**引擎零依赖**"——既诚实，又保住了可移植性，
而且这条新约束同样可以由测试自动强制。README 里的口径要同步改。

### 三个选项

| 选项 | 优点 | 代价 | 适合 |
| :--- | :--- | :--- | :--- |
| **tkinter**（标准库） | 连引擎都能保持零依赖；开箱即用 | 地图渲染、字体与纹理能力弱，做"沙盘"很吃力 | 先做**信息面板型**外壳（局势、菜单、日志、简易地图） |
| **pygame** | 2D 渲染舒服，生态成熟，做地图/动画顺手 | 引入第三方依赖；UI 控件要自己搭 | 想认真做 2D 地图与交互动效 |
| **Web（HTML + Canvas / WebGL）** | **排版与字体最强**（可直接嵌入隶书 webfont）、美术表现力最好、交互最自然 | 换技术栈；引擎要用本地服务喂数据 | 想让地图和书法真正好看 |

**建议路径**：**周期 5 先用 tkinter 做最小外壳**（成本最低，验证"数据 → 界面"这条链路），
等你确认要往"美术向"走，再评估迁到 Web。**不要第一步就上 WebGL**——那会让你三个月看不到进展。

## 七、设计方法：剧情与架空历史

### 7.1 三种历史取向，先选一个

| 取向 | 含义 | 玩家期待 | 你的现状 |
| :--- | :--- | :--- | :--- |
| 史实复刻 | 尽量还原历史 | 考据严谨，不允许穿越 | 不是 |
| **历史分叉（架空）** | 从某个点起历史改变 | 分叉要**讲得通**、后果要**推得下去** | ✅ **你在这里** |
| 完全架空 | 只借人物与地理符号 | 自由，但容易失去厚重感 | 可选 |

### 7.2 你现在的问题：分叉点没说清（这是必须补的一课）

现在开局写的是「**建安十三年（208）九月**」，但盘面是"蜀汉已据成都 / 汉中 / 江陵，关羽镇守江陵，魏都洛阳"。
对照史实：

- 208 年刘备**尚无根据地**（刚经历长坂，寄居荆州）；
- 益州在**刘璋**手里，汉中在**张鲁**手里；
- 关羽在 208 年并未镇守江陵；
- **洛阳此时是废墟**（董卓 190 年焚毁），曹操的根基在**邺城**，汉廷在**许都**；
  洛阳成为魏都是 **220 年曹丕称帝之后**的事；
- 顺带一句：「永安」这个地名是章武二年（222）由**鱼复**改名而来，208 年应称鱼复 / 江关。

**所以现在的设定本来就是架空的，只是没有把"从哪一刻开始不对"写下来。**
这不是错误，而是**缺一份声明**——没有它，考据型玩家第一眼就会出戏。

### 7.3 三个候选分叉前提（选一个，然后保持一致）

| 方案 | 分叉点 | 为什么现有盘面几乎自洽 | 代价 |
| :--- | :--- | :--- | :--- |
| **A（推荐）** | **建安二十四年（219）襄樊之战**：关羽水淹七军后，孙权**未背盟**（或吕蒙未能偷袭），蜀汉真正"跨有荆益"，《隆中对》构想成立；开局时间顺延到 **220–221 年** | ✅ 江陵属蜀且关羽在世 ✅ 汉中属蜀 ✅ 洛阳为魏都（220 年曹丕定都洛阳）✅ 东吴作为第三方需要外交拉拢 ✅ 曹魏据襄阳/樊城/宛城 | 需解释「上庸归属」（史实上 219 年蜀汉曾取上庸） |
| B | **建安十三年（208）赤壁之前**：曹操因后方叛乱撤军，刘备接管荆州北部并提前入蜀 | 保留现有开局年月 | 需要额外解释关羽在江陵、洛阳为都、蜀汉已立国，改动面更大 |
| C | 完全架空，不解释历史 | 最自由 | 失去考据的乐趣与真实感 |

> **决策建议**：选 A。它让 90% 的现有盘面**自动自洽**，而你只需要补一句分叉声明 + 一处上庸的解释。
> 这也说明一个道理：**架空不是随便改，而是"只改一个点，然后严格推演后果"。**

### 7.4 叙事怎么承载进一个策略游戏（三层）

策略游戏的剧情不是"看故事"，而是**在决策里感受到故事**。建议分三层落地：

| 层 | 载体 | 频率 | 写作要求 |
| :--- | :--- | :--- | :--- |
| **战略层** | 事件卡（阈值 / 连锁触发） | 每局 8~15 次 | 60~150 字；给玩家 2~3 个**有代价**的选择 |
| **人物层** | 将领台词、态度变化、结局评语 | 常驻 | 每人 3~5 条台词；忠诚 / 状态变化时切换语气 |
| **结局层** | 势力结局 + 每位将领结局 | 每局 1 次 | 结局文本要**回指玩家这一局做过的事**（"因你未救关羽，江陵终失"） |

### 7.5 历史锚点机制（把架空"推得下去"的关键工具）

不要写"随机历史事件"，而是设 4~6 个**锚点**，每个锚点 = 触发条件 + 2~3 个分支 + 后果：

| 锚点 | 触发条件（示例） | 分支 |
| :--- | :--- | :--- |
| 赤壁余波 | 第 3 回合 | 东吴索要荆州 / 曹魏报复性南征 |
| 入蜀 | 控制江陵且东吴好感 ≥ 60 | 刘璋求援 / 张鲁北犯 |
| 襄樊 | 攻占襄阳 | 关羽独进 / 孙权异动 |
| 夷陵 | 东吴背刺成功 | 复仇线 / 忍让线 |
| 北伐 | 打通粮道抵达洛阳 | 大捷 / 僵持 |

**这与你的"零随机"设计天然契合**：锚点用**条件**触发，不用骰子触发。
玩家能学会"我做了什么，才招来了这件事"——这正是确定性游戏最大的叙事优势。

## 八、设计方法：游戏性

### 8.1 先诚实诊断现状

| 症状 | 原因 | 后果 |
| :--- | :--- | :--- |
| 后期无望（压力棘轮） | 缺少减压手段 | 好局也输，玩家归因于"设计不公平"而不是"我操作差" |
| 可能"无脑点" | 练兵 / 募兵**没有代价** | 没有取舍 = 没有决策 |
| 决策总量偏少 | 20 回合 × 1 件大事 = 20 次关键决策 | 一局太短，学不到东西就容易结束 |

### 8.2 四个可用的杠杆

1. **每个选项都要有代价**。练兵不该只是 +5 精锐，应当同时消耗粮草或挤占将领任务位——
   有代价才有取舍，有取舍才有决策。
2. **用"信息不完全"替代"随机数"**（⭐ 对你最重要的一条，见下）。
3. **反馈要清晰**。玩家失误时，游戏必须告诉他"你输在哪一步"（日志、战报、结算提示）。
4. **目标要多样**。不要只有"打下洛阳"一种成功；加"守成""割据""汉室复兴"等评价维度，
   让不同的玩法都有出路（这也正好给"繁荣度"等内政系统一个存在的理由）。

### 8.3 ⭐ 关键洞察：零随机 ≠ 没有紧张感

你的硬约束是"不许有随机数"。但**紧张感不一定要来自运气，可以来自"我知道的不够"**：

> **把敌方兵力从"显示真实值"改成"显示情报估计值"。**
> 你看到的是"宛城守军约 8000（情报较旧）"，真实值可能是 11000。
> 派侦查粮道 / 侦查风向才能更新情报。

这样得到的是：
- **完全确定性**：没有骰子，同样的输入永远同样的输出，测试依然可断言；
- **真实的决策压力**：你是"冒险强攻"还是"先花一回合侦查"——这才是策略；
- **和现有系统天然咬合**：你已经有了「侦查粮道」「侦查风向」两条情报线，
  把"情报"从"解锁计谋的钥匙"扩展成"决策依据"，是**极小改动换极大体验提升**。

### 8.4 一局应该有多长

20 回合对"学习一局并复盘"其实偏短。建议在数值稳定后考虑：
**主线 20 回合（速通）+ 编年模式 40~60 回合（完整北伐）**。
先别急着加，等压力棘轮修好、数据统计脚本跑出结局分布后再决定。

## 九、设计方法：数值与平衡

### 9.1 方法：单变量实验 + 批量对局 + 表格记录

**不要凭感觉调数值。** 用你已经有的工程能力：

```bash
python main.py --demo                    # 单局快速验证
python tools/模拟统计.py --配置 A --局数 200   # 周期 2 要写的批量统计
```

统计脚本至少输出：

| 指标 | 为什么重要 |
| :--- | :--- |
| 四档结局的**分布比例** | 如果 95% 都是"星落秋风"，说明设计有问题，不是玩家菜 |
| 压力 / 兵力 / 粮草 / 扩张倾向 的**每回合曲线** | 找到"崩盘点"出现在第几回合 |
| 各策略路线（纯军事 / 纯计谋 / 内政优先）的**成功率** | 验证是否有多条可行路线 |
| 首次破局的回合数 | 一局的有效决策时长 |

### 9.2 基准线与实验纪律

1. 先记录**当前版本**的基线数据（改之前一定先测一遍）；
2. **一次只改一个变量**（例如只改"议和减压量"），改完立刻重测；
3. 把结果记进一张表（`docs/数值实验记录.md` 可以新建），注明日期、改动、前后对比；
4. 数值改动**优先走 `config/`**，不要改代码里的判定逻辑；
5. 每次改完，126 项自测 + 74 个用例必须全绿（断言不许削弱）。

### 9.3 压力棘轮的具体数值解法（供周期 2 参考）

现在的问题本质是：**压力的"进水口"（扩张倾向 >70 时 +5/回合）远大于"出水口"（劫粮道 -10 扩张倾向）**。
可选组合：

- **加出水口**：议和 / 迁都 / 连环计（玩家可控，有参与感）—— 推荐；
- **软化上限**：压力 >80 后每回合自然 -1~-2（改动最小，但玩家无参与感）；
- **削进水口**：扩张倾向 >70 的判定阈值上调到 >80（最小改动，但浅）；
- **健康标准**：修完之后，四档结局**都应该能出现**，且"打得好 → 能到北伐大捷"这条因果链清晰。

## 十、设计方法：AI 逻辑

### 10.1 三层结构（把你的阈值脚本升级成正经的 AI）

```
感知（读状态） → 评估（势力值 / 威胁 / 机会） → 行动（选择策略）
```

| 层 | 曹魏 | 东吴 |
| :--- | :--- | :--- |
| 感知 | 玩家兵力、控制城池、前线兵力差、粮道状态 | 蜀魏势力比、自身观望值、好感、盟约状态 |
| 评估 | 哪座城最危险、是否要增兵、是否发动南征 | 该倒向谁、要不要主动接触 |
| 行动 | 兵力调度、增援、进攻（构想池第 9 条） | 派使谈判、索要荆州、背刺（构想池第 8 条） |

### 10.2 两条铁律

1. **AI 必须是 `(状态) → 决策` 的纯函数**：给定同样的局面，AI 永远做同样的选择。
   这样它才可测试、可复盘，也不会破坏"零随机"的架构约束。
2. **AI 的每个决策都要能被解释**：在日志里写明理由
   （例如 `东吴：势力比 0.72 < 0.8 → 转亲蜀；好感 74 > 70 → 提出结盟`）。
   玩家看得懂 AI 在怕什么、图什么，游戏才有博弈感。

### 10.3 测试方式

既然 AI 是纯函数，就可以直接断言：**给定状态 → 期望决策**。
你的 `tests/` 里已经有东吴三态外交的用例，扩展成"兵力调度"与"主动外交"是同一套写法。

## 十一、自我提醒：这个项目最容易踩的坑

1. **不要把代码和美术放在同一个周期里做** —— 两件事的"完成标准"不同，混在一起两件都做不完。
2. **不要在改数值的同时改结构** —— 出了问题你会分不清是数值错了还是代码错了。
3. **不要在大改玩法时顺手重写引擎** —— 引擎已经稳定，它是你的安全垫。
4. **不要在尺寸未定时批量画 UI** —— 那是最容易全废的一类工作。
5. **不要过早做全中国地图** —— 先把汉中—襄阳这一条轴线做到有质感。
6. **不要为了"看起来更像游戏"而牺牲确定性** —— 零随机是这个项目最独特的地方，
   紧张感应该来自"信息不完全"，不是来自骰子。
7. **每个周期结束都要提交并更新 CHANGELOG** —— 半年后回来看，只有仓库记得你做过什么。
8. **每完成一个玩法改动，先问一遍**：这一局玩家输了，他能不能说清楚"我输在哪一步"？
