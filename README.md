## 一、项目简介

### 这是什么

《三国·蜀汉突围》是一个**控制台回合制策略游戏**：公元 208 年（建安十三年）九月，蜀汉以绝对劣势兵力北伐。
玩家在每回合面对有限的"大事"名额，需要在四类决策之间取舍——**部署将领任务**、**设定守城指令**、
**发动军事行动**、**施展计谋或外交**——然后在 20 回合内争取攻占曹魏首都洛阳。

游戏本体、配置系统、存档系统与测试体系**全部只使用 Python 标准库**，
没有任何第三方依赖，也没有图形界面：`git clone` 之后 `python main.py` 就能玩。

### 它解决什么玩法需求

大多数策略游戏的"策略"会被随机数稀释：命中率、暴击、掷骰子决定了成败，玩家难以复盘"我到底哪一步走错了"。

这个项目刻意反过来做了一件事——**零随机（Zero-Randomness）**：

- **没有任何随机数调用**。全仓库生产代码中不出现 `random` 字样，并有自动化测试逐行扫描来强制保证；
- **计谋 = 前置条件检查**：有粮道情报才能劫粮道，守将忠诚 <5 且使臣智谋 ≥8 才能劝降。条件达成即 100% 成功；
- **军事 = 阈值比较**：进攻兵力 > 守军×1.5 强攻必胜，>×0.8 可围攻，<×0.5 直接判必败并禁止送死；
- **结算流水线固定 13 步**，顺序不可变。

于是**同一个局面 + 同一个决策 = 同一个结果**。这让游戏变成一道可以被推理、被复盘、被共享题解的题：
你可以把某个局面贴给朋友说"这局我该怎么走"，对方能在自己机器上复现出完全一样的盘面。
这一点也是整个工程设计的支点——**确定性让自动化测试成为可能**：
测试可以断言"输入这 3 回合的指令序列，第 4 回合必然是这个结局"。

### 技术要点一览

| 维度 | 说明 |
| :--- | :--- |
| 语言 / 依赖 | Python（纯标准库，第三方依赖 **0**） |
| 代码结构 | 单文件三段式（状态定义 / 确定性判定 / 主循环）+ 配置层 + 存档层 + 测试体系 |
| 规则版本 | `v0.3.0`（玩法规则） |
| 工程发布版本 | `v1.0.0`（工程化里程碑，玩法未变） |
| 规模 | 游戏主程序约 1450 行，配置加载器约 460 行，存档模块约 450 行 |
| 测试 | 126 项自断言自测 + 74 个 unittest 用例，一键入口 |
| 可配置项 | 兵种 / 计谋 / 季节 / 外交 / 战斗 共 5 类数值抽到 JSON，改数值不必改代码 |

## 二、如何运行

### 环境要求

- **Python 3.7 或更高**（开发与验证环境：Python **3.13.1** / Windows 11。
  代码未使用任何高版本独有语法，也没有类型注解，因此低版本理论上同样可用，但未做多版本兼容矩阵实测）
- **不需要安装任何第三方库，也不需要虚拟环境**
- Windows 控制台建议使用 UTF-8 编码（程序内已做尽力而为的编码设置）

### 安装依赖

本项目**没有第三方依赖**，`requirements.txt` 只是显式声明这一事实：

```bash
python -m pip install -r requirements.txt   # 可安全执行，不会安装任何包
```

> 这条声明不是口头承诺：`tests/test_architecture.py` 会逐行扫描生产代码的 `import` 语句，
> 一旦混入非标准库、非本地模块的导入，测试立刻失败。

### 启动游戏

```bash
# 1. 拿到仓库
git clone <你的仓库地址>
cd 三国test

# 2. 确认环境（只需 Python）
python --version              # Windows 若无 python 命令，可用 py --version

# 3. 开始玩（不带参数 = 新开局，交互模式）
python main.py                # macOS / Linux 亦可 python3 main.py

# 4. 跑测试
python run_tests.py --fast     # 约 11 秒；完整版 python run_tests.py 约 82 秒
```

### 命令行参数

| 参数 | 说明 |
| :--- | :--- |
| *(不带参数)* | **新开局**：交互模式，启动后询问"扮演幕僚 / 自动演示" |
| `--demo` | **自动演示**：无人值守推演满 20 回合，适合录屏与冒烟验证 |
| `--load [存档名]` / `-l` | 从 `saves/<存档名>.json` **继续同一局**；省略名字时读 `save1`（`--load` 优先于 `--demo`） |
| `--list-saves` | 列出 `saves/` 下全部存档及其状态（正常 / 损坏）后退出 |
| `--check-config` | 校验配置文件后退出；有问题返回码 1 并逐条列出 |
| `--config <目录>` | 使用指定配置目录（默认为项目根目录下的 `config/`） |
| `--log-level <级别>` | 日志级别 `DEBUG`/`INFO`/`WARNING`/`ERROR`，默认 `WARNING` |
| `--version` | 显示工程发布版本与游戏规则版本 |
| `--help` / `-h` | 显示全部参数说明 |

**日志说明**：用标准库 `logging` 输出到 **stderr**，默认 `WARNING`（不刷屏）。
`--log-level INFO` 会记录启动、配置加载、每回合关键状态、存档读写与最终结局。
日志**不替代**面向玩家的中文提示：出错时仍会打印可操作的中文说明，日志只是附带的技术记录。

## 三、怎么玩

### 第一步：选择运行模式

启动后程序会问你怎么玩：

- 输入 `1` → **扮演幕僚**：逐回合自己下指令，完整参与决策
- 输入 `2` → **自动演示**：按内置默认策略推演 20 回合，无人值守（等价于 `python main.py --demo`）

### 第二步：每回合的决策菜单

```
1. 部署将领任务（可多次）
2. 设定守城指令（可多次）
3. 军事行动【大事】
4. 计谋【大事】
5. 外交【大事/轻量】
6. 结束本回合决策，推进结算
7. 存档 / 读档【轻量】
```

- 每回合只能执行**一件"大事"**（军事 / 计谋 / 外交）——这是核心取舍：这一回合是练兵、是劫粮、还是攻城？
- 部署将领任务与设定守城指令**不限次数**，但每位将领每回合只能有一个任务
- 输入 `6` 结束决策，系统自动结算 13 步、清屏打印新局势，然后进入下一回合
- 第 `7` 项存档 / 读档**不占**"大事"名额

### 核心规则速览

**开局（建安十三年九月 · 秋季）**

| 势力 | 兵力 | 粮草 | 关键指标 |
| :--- | :--- | :--- | :--- |
| 蜀汉 | 18000（含永安 3000） | 80 | 魏国压力 30、东吴好感 40、民心 100、精锐比例 0% |
| 曹魏 | 80000 | 200 | 扩张倾向 60 |
| 东吴 | 50000 | 120 | 观望态度 50 |

曹魏城池：襄阳(7000/曹仁)、宛城(8000/侯音)、樊城(6000/张郃)、上庸(4000/夏侯尚)、**洛阳(12000/曹真，首都)**。
蜀汉固有城池：成都、江陵、阆中、汉中、永安。

**将领（6 位）**

| 将领 | 统御 | 智谋 | 内政 | 忠诚 | 驻地 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 关羽 | 9 | 6 | 4 | 10 | 江陵 |
| 张飞 | 8 | 3 | 2 | 10 | 阆中 |
| 诸葛亮 | 5 | 10 | 9 | 10 | 成都 |
| 魏延 | 7 | 5 | 3 | 8 | 汉中 |
| 赵云 | 8 | 7 | 4 | 10 | 永安 |
| 黄忠 | 7 | 4 | 2 | 9 | 成都 |

任务效果：**镇守城池**＝防御加成 统御×10%；**驻守险关**＝防御加成 统御×20% 且全国军粮消耗减半；
**北伐先锋**＝进攻损耗 −30%；**后方屯田**＝每回合粮草 +内政×2×民心/100；
**练兵**＝每回合兵力 +统御×5；**外交使节**＝每回合东吴好感 +智谋×2。
镇守城池还可选子任务：无 / 练兵（精锐比例 +5，上限 100）/ 募兵（兵力 +200、粮草 −20）。

**军事行动（确定性判定）**

| 条件（进攻兵力 vs 守军） | 结果 |
| :--- | :--- |
| > 守军×1.5 | **强攻必胜**，损失＝守军×0.8 |
| > 守军×0.8 | 可**围攻**，3 回合后破城（期间持续耗粮） |
| 0.5× ~ 0.8× | 无必胜把握，系统**禁止进攻** |
| < 守军×0.5 | **必败**，禁止送死；仅可选「死士突袭」（固定牺牲部队或将领） |

出征兵力＝**有效兵力**×60%，有效兵力＝兵力×(1+精锐比例/100)；守城方同样按有效兵力计算。

**计谋（前置条件达成即 100% 成功）**

| 计谋 | 前置条件 | 效果 |
| :--- | :--- | :--- |
| 侦查粮道 | 粮草 ≥10 | 花 1 回合与粮草 10，获得粮道情报 |
| 劫粮道 | 拥有粮道情报 | 曹魏兵力 −30%、粮草 −20、扩张倾向 −10 |
| 侦查风向 | 粮草 ≥10 | 花 1 回合与粮草 10，获得风向情报 |
| 火攻 | 拥有风向情报 | 曹魏兵力 −25%、粮草 −30、扩张倾向 −15 |
| 据险而守 | 将领在汉中/阆中 且 任务为驻守险关 | 该将领防御加成翻倍 |
| 劝降 | 守将忠诚 <5 且 使臣智谋 ≥8 | 城池归蜀、守军加入（仅宛城侯音满足） |

**每回合自动结算（13 步，顺序固定）**：曹魏增长 → 粮草与冬季 → 将领任务 → 东吴骑墙 → 田忌赛马
→ 围攻推进 → 曹魏进攻 → 东吴背刺 → 重伤恢复 → 民心恢复 → 连锁计时 → 阈值事件 → 东吴均势外交 AI。

**季节与冬季**：开局建安十三年九月，每回合月份 +1、>12 进位次年。9~11 秋、12~2 冬、3~5 春、6~8 夏。
冬季军队在外粮草消耗 ×1.5 且兵力冻伤 −2%（退守则 ×1.25 / −1%）。

**结局（4 档，优先级从高到低）**

1. **北伐大捷**——攻下洛阳（曹魏兵力 ×0.5、东吴观望归零、蜀汉兵力 +5000）
2. **星落秋风**——兵力归零 或 魏国压力 >100
3. **汉家尚有可为**——满 20 回合且兵力 >18000（超过初始值）
4. **中性结局**——满 20 回合但兵力未超过初始值

> 完整规则速查表（含阈值事件、东吴均势 AI 的三态判定表、城破伤亡指令）见
> [`docs/规则说明.md`](docs/规则说明.md)。

## 五、已实现的机制

规则版本 **v0.3.0**，以下机制均可在游戏中实际触发，并被自动化测试覆盖。

| # | 机制模块 | 状态 | 说明 |
| :-- | :--- | :-- | :--- |
| 1 | **回合制主循环** | ✅ | 决策阶段 → 13 步自动结算 → 打印局势 → 结局判定 → 推进日期；固定 20 回合上限 |
| 2 | **建安年月与季节系统** | ✅ | 年 / 月 / 回合计数 / 季节联动，月份进位跨年，首次入冬弹出「冬至」提醒 |
| 3 | **三方势力与城池归属** | ✅ | 蜀汉 / 曹魏 / 东吴三方数值；5 座曹魏城池（含首都洛阳）+ 5 座蜀汉固有城池 |
| 4 | **武将属性系统** | ✅ | 6 位将领 × 统御 / 智谋 / 内政 / 忠诚 / 驻地 / 状态 |
| 5 | **将领任务系统** | ✅ | 6 种任务（镇守城池 / 驻守险关 / 北伐先锋 / 后方屯田 / 练兵 / 外交使节）+ 镇守子任务（练兵 / 募兵） |
| 6 | **确定性战斗判定** | ✅ | 强攻 / 围攻 / 必败三档阈值，全部为纯函数；有效兵力 = 兵力 ×(1+精锐比例/100) |
| 7 | **攻城与收编结算** | ✅ | 破城后收编降卒（守军×0.5）、缴获粮草；城破伤亡按"提前撤退/死守/默认驻守"三档确定化 |
| 8 | **计谋系统** | ✅ | 6 种计谋，前置条件达成即 100% 成功；「死士突袭」为必败局面下的殊死手段 |

## 六、测试情况

### 一键运行

```bash
python run_tests.py           # 全部用例（含原 126 项自测全量回归），实测约 82 秒
python run_tests.py --fast    # 跳过旧自测全量回归，实测约 11 秒（改代码时用这个）
python -m unittest discover -s tests -v      # 等价的标准库入口
```

输出给出 **总数 / 通过 / 失败 / 错误 / 跳过 / 用时**，有失败时逐条列出用例名与原因；
退出码 `0` 表示全绿、`1` 表示有失败，**可直接接入 CI 或 git hook**。

### 最近一次验证结果（本机实测，可复现）

```
python run_tests.py         → 总数：74 ｜ 通过：74 ｜ 失败：0 ｜ 错误：0 ｜ 用时：81.9 秒
python run_tests.py --fast  → 总数：70 ｜ 通过：70 ｜ 失败：0 ｜ 错误：0 ｜ 用时：10.9 秒
python 自测_确定性判定.py    → 全部 126 项自测通过。
```

### 覆盖了什么

测试分成两层，**互不替代**：

**第一层：原 126 项自断言自测（`自测_确定性判定.py`，可单独运行）**
用自研的 `断言()` + 章节组织，覆盖十个方面：
【一】战斗判定规则 19 项、【二】城池与势力 5 项、【三】将领任务 8 项、【四】外交 5 项、
【五】整局模拟 12 项、【六】冬季与月份 16 项、【七】东吴 AI 16 项、【八】态势图 1 项、
【九】配置系统 21 项、【十】存档系统 23 项，外加 1 项"全文件不含 `random` 字样"的零随机校验。

做法是**注入式测试**：用 `importlib` 动态加载游戏模块（不触发主循环）→ 把 `模块.input` 换成脚本输入队列
→ 用 `contextlib.redirect_stdout` 捕获输出 → 跑完整 20 回合对局并断言结局。
配置部分用临时目录造出各类非法配置；存档部分做「保存 → 篡改 → 读档」往返比对与损坏注入。

**第二层：`tests/` 分类用例（unittest，74 个）**

| 文件 | 类别 | 覆盖内容 |
| :--- | :--- | :--- |
| `test_rules.py` | 规则 | 强攻/围攻/必败阈值语义、攻城与防御加成、将领任务与城破伤亡、计谋前置条件、东吴三态外交、势力值与城池统计、月份跨年、态势图渲染 |
| `test_boundaries.py` | 边界 | 阈值临界值（恰好 ×1.5 / ×0.8 / ×0.5）、兵力与粮草极值、配置数值上下界、空值与异常输入 |
| `test_endings.py` | 结局 | 4 档结局各自的触发路径与优先级 |
| `test_regressions.py` | 回归 | **固化已修过的真实缺陷**，防止再次复发（见下表） |
| `test_architecture.py` | 架构 | 零随机逐行扫描、不导入随机库、仅标准库依赖、生产模块可编译、同输入结果稳定、两次加载初始状态一致 |
| `test_legacy_suite.py` | 回归 | 把原 126 项自测整体执行并核对"通过"与断言数基线（不低于 126） |

### 「零随机」是被自动强制的，不是口头承诺

架构测试用三层手段保证确定性，任一层被破坏都会让测试变红：

1. **逐行扫描**生产模块源码，命中 `random` / `randint` / `shuffle` / `choice` / `seed` 等关键字即失败，
   并报出 `文件:行号:内容`；
2. **禁止导入**随机库（`import random` / `from secrets` 等）；
3. **行为级校验**：同一输入连续调用两次判定函数，结果必须完全一致。

> 这套检查还带**自检**：测试会验证"关键字白名单"只放过 `choices=` 这类合法的 argparse 关键字参数写法，
> 而真正的 `random.choices(...)` 调用依然会被判定为违规——避免白名单本身成为漏检的后门。

### 回归用例固化了两个真实缺陷

这两个 bug 都是测试先行发现、修掉后立刻写成回归用例的（详见 [`CHANGELOG.md`](CHANGELOG.md)）：

| 缺陷 | 现象 | 修复 |
| :--- | :--- | :--- |
| 非法配置泄漏（M2） | 非严格模式下只做了**部分合并**，非法字段虽被报错，但仍可能带着非法值进入判定逻辑，导致"配置错了却不崩、只是算错" | 改为**整体回退**内置默认值：任一处非法即整份配置失效，行为可预期 |
| 存档必填字段差异（M3） | 存档校验对所有城池区块套用了同一份必填字段，而"敌方城池"用 `守军`、"蜀汉城池"用 `兵力` → **所有存档都被判为损坏、根本读不出** | 引入**分区块契约**（每个区块各自的必填字段），并补回归用例锁死 |

### 测试环境与已知短板

- 实测环境：Python 3.13.1 / Windows 11；全量耗时主要花在游戏内每回合 0.5 秒的显示停顿上。
- 使用标准库 `unittest`，**未引入 pytest**（保持零依赖）；`run_tests.py` 提供统一的汇总输出与退出码。
- **目前没有 CI 配置文件**：一键入口与退出码已经就绪，接 GitHub Actions 只需几行 YAML。

## 七、配置与存档

### 配置：改数值不必改代码

五类数值全部抽到 `config/` 下，代码只读配置、不再写死数字：

```bash
python main.py --check-config              # 校验配置合法性
python main.py --config ./我的配置          # 用另一套配置运行
```

| 文件 | 内容 |
| :--- | :--- |
| `config/units.json` | 兵种与精锐比例、练兵、募兵数值 |
| `config/schemes.json` | 计谋的前置条件与效果 |
| `config/seasons.json` | 季节月份划分与冬季惩罚档位 |
| `config/diplomacy.json` | 东吴三态阈值与外交事件参数 |
| `config/battle.json` | 强攻/围攻/必败/破城倍率、进攻损失与收编系数、防御加成、守军比例 |

**校验覆盖范围**：文件存在性、JSON 语法、字段类型、数值范围、枚举合法、列表元素类型、
交叉引用（如计谋前置情报必须在情报键名中）、顺序一致性（如强攻倍率 > 围攻倍率 > 必败倍率、季节月份必须不重不漏覆盖 1~12 月）、未知字段（多为拼写错误）。

**非法配置的行为**：`--check-config` 会返回码 1 并逐条列出
「`<文件>` → 字段 `"<路径>"`：期望 `<...>`，实际 `<...>`」；游戏运行时若配置非法，
**不会崩溃**，而是打印明确中文提示并**整体回退**内置默认值继续运行。

### 存档：保存 → 退出 → 重新加载 → 继续同一局

```bash
python main.py                     # 游戏中：决策菜单第 7 项 → 存档
python main.py --list-saves        # 查看有哪些存档、是否损坏
python main.py --load 我的存档      # 从存档继续，日期/兵力/粮草/事件进度全部还原
```

- **格式**：可读 JSON（记事本直接打开），顶层含 `存档版本`（当前 `1`）、`游戏版本`、`保存时间`、
  日期（年月/回合/季节）、三方势力、敌方城池、蜀汉城池、将领们、情报、全局状态。
- **写入安全**：先写 `.tmp` 再 `os.replace` 原子替换，不会写一半把已有存档写坏。
- **异常处理**：文件不存在 / JSON 语法错 / 顶层不是对象 / 缺必填字段 / 字段类型错 / 版本不支持，
  每种情况都给可读中文提示（含文件路径与建议），**绝不抛 traceback，也不破坏当前局面**。
- **旧版本兼容**：读档前先比对 `存档版本` 与支持列表；已预留 `迁移表` 作为版本迁移钩子
  （当前无历史存档版本，因此为空），未登记迁移的旧版本会被明确拒绝并说明支持的版本。

### 8.1 职责分工

### 8.2 我是怎么"驾驭" AI 的

把需求丢给 AI 谁都会，难的是**让 AI 的产出可控、可验证、可回退**。我在这个项目里坚持了四件事：

**1）阶段化交付 + 不可谈判的约束。**
我把项目拆成 M1~M5 五个里程碑，每个里程碑开工前先给 AI 一份带硬约束的"任务书"，其中反复出现的是：
不许引入任何第三方依赖、不许改动游戏规则与数值平衡、**不许削弱或删除已有测试（断言数量只能增不能减）**、
不许做大规模重构、每完成一步必须给出可复现的验证证据。
正是"不许削弱已有断言"这条约束，让 M4 的测试工程化没有变成"把跑不过的用例删掉"。

**2）把"承诺"翻译成"机器能检查的断言"。**
"这个游戏没有随机性"是一句人话，但人话会过期。我要求 AI 把它变成可执行的检查：逐行扫描源码中的随机关键字、
禁止导入随机库、同输入两次调用结果必须一致——三条断言全部落在 `test_architecture.py` 里，任何人改坏都会立刻变红。
类似的还有"仅标准库"：`requirements.txt` 写着 0 依赖，测试则逐行检查 `import` 语句，**声明与校验成对存在**。

**3）要求 AI 给检查本身也加自检。**
AI 写的检查也可能有洞。架构测试里那条"关键字白名单"一度把 argparse 的 `choices=` 参数误判成随机调用；
修好之后我要求补一条自检用例——**验证白名单只放过合法写法、真正的随机调用依然会被抓住**。
"检查者也要被检查"是我从这段协作里得到的最实用的一条经验。

**4）用测试兜住改动，用回归用例固化教训。**
AI 改代码很快，但快就容易碰坏别处。这个项目里有两个真实缺陷是**测试先发现的**，修完之后立刻被写成回归用例：
一个是非法配置只做了"部分合并"，导致非法值可能溜进判定逻辑；另一个是存档校验对所有城池套用同一份必填字段，
导致"敌方城池用守军、蜀汉城池用兵力"的差异让**所有存档都被判为损坏**。
它们现在被 `test_regressions.py` 永久锁住——同一个错误不可能犯第二次。

### 8.4 我对 AI 生成代码的边界认识

- **AI 明显更强的部分**：重复性实现（字典与菜单的铺量）、测试脚手架、文档整理、把规范落到细节（校验、报错文案、边界处理）。
- **必须由人负责的部分**：玩法的乐趣判断、数值平衡的取舍、"这个机制好不好玩"——这些没有标准答案，
  AI 无法替我承担后果，所以我坚持自己玩、自己判断。
- **我的自我要求**：**AI 写的每一行代码，我都要为它负责**。所以我要求每一处承诺都有对应的测试，
  每一个里程碑都有可复现的验证命令。这样才能在面试中坦然地说：
  这个项目是我用 AI 作为工程杠杆做出来的，而不是"AI 做完之后我签了个名"。

## 十、已知限制

**当前不做什么**（如实列出，避免误解）：

- **无图形界面**，只有控制台交互；不支持鼠标操作。
- **配置覆盖范围有限**：结算经济数值（曹魏增长率、粮草消耗基数、粮荒阈值、压力增减、阈值事件、
  连锁计时、民心恢复）、任务名枚举、城池与将领数据、结局阈值仍在代码中，需改代码而非配置。
- **配置为整体校验**：任一处非法即整体回退内置默认值（不做"部分生效"），以行为可预期为优先。
- **启动期派生量需重启**：`险关位置` 等派生量在进程启动时读取；运行中修改配置文件需重启进程生效。
- **存档范围有限**：单一 `saves/` 目录、无自动存档、无云同步；存档不记录 `config/` 快照，
  因此改配置后读旧档会按新配置运行；手工新增的未知字段会被原样保留（不做多余字段校验）。
- **固定 20 回合上限**，无自由模式、无难度选择。
- **单机本地运行**，无联网、无排行榜、无多人。
- **仅中文一种语言**，无音效与美术资源。
- **没有 CI 配置**（一键入口 `run_tests.py` 与退出码已就绪，可直接接 GitHub Actions）。
- **没有 LICENSE 文件**（如需授权请自行补充）。
- `docs/待实现构想.txt` 中的内容均为**未实现设想**，不代表现有功能。
